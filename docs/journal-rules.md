# 작업 일지 작성 규칙

여러 에이전트가 함께 씁니다. 작업 일지는 개별 날짜별 파일(`docs/journal/YYYY-MM-DD.md`)로
분할 관리되며, [journal-ko.md](journal-ko.md)는 전체 마일스톤과 목차를 조망하는 마스터 대시보드입니다.
이 파일은 그 규칙만 담습니다 — 일지 본문은 항목이 쌓이면서 계속 길어지므로, **규칙을 읽으려고 일지를
통째로 컨텍스트에 올리지 마세요.**

## 언제 쓰나

의미 있는 작업 단위가 끝날 때마다 씁니다. 학습을 돌렸을 때, 뭔가 막혔다 풀렸을 때,
숫자를 쟀을 때, 예상이 빗나갔을 때.

**쓰지 않는 경우**: 단순 조회, 파일 읽기, 아무것도 바뀌지 않은 작업.
일지는 활동 기록이 아니라 **다음 사람이 시간을 아끼는 데 쓰는 자료**입니다.

## 어디에 쓰나

1. **당일 날짜 파일(`docs/journal/YYYY-MM-DD.md`) 맨 끝에 덧붙입니다.**
   - 파일이 없으면 `# 작업 일지 — YYYY-MM-DD` 헤더와 `[← 전체 작업 일지 목차로 돌아가기](../journal-ko.md)` 링크를 달고 새로 생성합니다.
   - 기존 작성된 내용은 절대 수정하지 않습니다.
2. **마스터 인덱스([journal-ko.md](journal-ko.md))를 함께 업데이트합니다.**
   - `마일스톤 요약` 테이블이나 `날짜별 상세 목차`에 해당 일자 및 핵심 요약 1줄을 추가/반영합니다.
3. **이미지/영상 등 미디어 파일**:
   - 미디어 파일은 `docs/media/`에 저장하고, 개별 일지(`docs/journal/YYYY-MM-DD.md`)에서는 상대 경로 `../media/<파일명>`으로 참조합니다.

여러 에이전트가 동시에 쓰므로 이 규칙이 병합 충돌과 문서 비대화를 최소화합니다. 충돌이 나면
**양쪽 항목을 모두 남기고** 날짜순으로 정렬하세요. 어느 쪽도 버리지 않습니다.

## 항목 형식

```markdown
## YYYY-MM-DD — 한 줄 요약

**하려던 것**

**한 것**

**막힌 것** — 증상 → 원인 → 해결

**측정값**

**다음**
```

다섯 항목 중 **`하려던 것` / `한 것` / `다음`은 필수**입니다.
`막힌 것`과 `측정값`은 해당 사항이 없으면 생략합니다.

한 줄 요약은 목차에서 이 항목을 찾을 수 있을 만큼 구체적으로. "학습 실험"이 아니라
"air_time 3.0→6.0, 보폭은 커졌지만 접지 불안정".

## 내용 규칙

**명령어는 그대로 붙여넣습니다.** 요약하지 말고 실행한 문자열 그대로,
```bash 펜스 안에. 몇 주 뒤에 플래그 조합은 아무도 기억 못 합니다.

**숫자에는 단위를 붙입니다.** "느렸다"가 아니라 "45.7 s/iter". "메모리를 많이 썼다"가
아니라 "워커당 RSS 1.4 GB". 재지 않았으면 **"안 재봤다"라고 명시**하세요.
추측을 측정처럼 적지 않습니다.

**빗나간 예상을 반드시 적습니다.** 이건 선택이 아니라 규칙입니다. 예상과 결과가
달랐다면 둘 다 적으세요 — 그럴듯한 추론이 어디서 깨지는지가 이 파일의 가장 큰
가치입니다. 예:

> **예상이 틀린 것** — 효율코어가 동기 all-reduce의 발목을 잡아 6워커가 최적일
> 거라 예상했다. 8워커가 더 빨랐다(10.8 vs 11.9 s).

**실패한 시도도 적습니다.** 되돌린 변경, 버린 접근, 잘못 짚은 원인 전부.
다음 사람이 같은 길을 다시 걷지 않게 하는 게 목적입니다.

**로그는 결정적인 줄만 잘라 넣습니다.** 전체 출력을 붙이지 마세요. 판단의 근거가 된
몇 줄이면 충분합니다.

**커밋은 SHA로 참조합니다** (`ba652ec9`). "아까 그 커밋"은 나중에 아무 의미가 없습니다.

**넣지 않는 것**: 토큰·API 키·비밀번호, 개인정보, 다른 곳에 이미 있는 내용
(코드 구조, git 히스토리, AGENTS.md에 적힌 것)의 재서술.

## 다듬지 않습니다

일지는 **"그때 실제로 이랬다"**의 기록입니다. 문장을 매끄럽게 만들려다 구체적인
사실이 사라지는 게 가장 흔한 실패입니다. 거친 문장에 정확한 숫자가 낫습니다.

**나중에 결론이 뒤집혀도 옛 항목을 고치지 않습니다.** 새 항목을 쓰고 날짜로
참조하세요:

> 2026-09-07 항목의 "게이트 문턱 0.15~0.3" 추정은 틀렸다. 실제로는 …

틀린 기록이 남아 있는 것이 기록이 조용히 바뀌는 것보다 낫습니다.

## 수확 규칙

일지의 내용이 **반복해서 확인되거나 확실히 자리를 잡았을 때만**
[getting-started-ko.md](getting-started-ko.md)로 옮깁니다.

- 일지 = 검증 안 된 것도 들어감. 틀려도 됨.
- 입문 문서 = 검증된 것만. 믿을 수 있어야 함.

한 번 해보고 잘 된 것을 바로 입문 문서에 쓰지 마세요. **처음부터 입문 문서에
쓰는 일은 없습니다.** 일지를 거쳐 갑니다.

## 커밋 전 체크리스트

- [ ] 당일 날짜 파일(`docs/journal/YYYY-MM-DD.md`) **맨 끝**에 덧붙였는가 (기존 항목 수정 없음)
- [ ] 마스터 대시보드([journal-ko.md](journal-ko.md))의 목차 또는 요약에 반영했는가
- [ ] 날짜와 한 줄 요약이 있는가
- [ ] `하려던 것` / `한 것` / `다음`이 채워졌는가
- [ ] 명령어를 그대로 넣었는가
- [ ] 숫자에 단위가 있는가, 안 잰 건 안 쟀다고 적었는가
- [ ] 예상이 빗나갔다면 그 사실을 적었는가
- [ ] 미디어 링크가 `../media/<파일명>` 형태이며 파일이 존재하는가
- [ ] 비밀 정보가 없는가

## 언어

한국어로 씁니다. 명령어·로그·식별자·코드는 원문 그대로 둡니다.
